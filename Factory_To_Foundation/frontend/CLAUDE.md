## 1. What Factory » Foundation Is, Right Now

A React 19 / Vite / TypeScript / Tailwind v4 single-page app. One shared application shell (`FeaturePage`) that every feature renders through — a slim command ribbon at the top, a three-panel resizable workspace below (Browse / Viewport / Selected), all styled through one design token system. Eleven features are routed; all eleven now have real UI (Analytics/Administration/Reports shipped this pass, see §6.9) — `ComingSoonPage` remains on disk, unused by any route, for whatever feature is unbuilt next.

```text
Sidebar (collapsible icon rail) ── routes to ──▶ FeaturePage
                                                    ├── CommandRibbon (dropdown menus + page identity)
                                                    └── Workspace (resizable, fully collapsible)
                                                          ├── Left:   Browse panel
                                                          ├── Center: Viewport (camera pan/zoom/fit)
                                                          └── Right:  Selected/Inspector panel
```

## 3. The Framework Layer — What Each Piece Owns

Built incrementally, each promoted to `framework/` only once a second (or third) real feature needed the identical thing — never spec'd in the abstract ahead of a real consumer.

- **`Viewport`** (`framework/viewport`) — owns camera state (`{x, y, zoom}`), left-drag pan, cursor-anchored wheel zoom, double-click fit-to-content, auto-fit on mount/bounds-change. Clips its content; the camera moves, nothing ever overflows the browser. `useCamera()` hook for any child to read/drive it.
- **`EntityCanvas` / `EntityNode`** (`framework/viewport`) — the generic "nodes positioned in world-space, connected by optional edges, click to select" renderer. Originally bespoke per-feature (`GraphNode`/`GraphCanvas`, `FactoryNode`/`FactoryCanvas`); promoted to `framework/` once Robotics/Logistics/Construction/Assets/Scheduling all needed the same shape at once. Genealogy still uses its own bespoke node component (`GraphNode`) because it existed before the promotion and has feature-specific visual treatment (tier-colored borders) that doesn't fit the generic component's props — not a gap, a deliberate non-migration. Factory's `FactoryNode`/`FactoryCanvas` (the abstract 2D block equivalent) no longer exist at all — deleted once Factory's center viewport became real 3D digital-twin geometry instead, see §6.10.
- **`Workspace`** (`framework/workspace`) — three-panel resizable layout via `react-resizable-panels`. **All three panels are `collapsible` with `collapsedSize={0}`** — drag any divider fully closed, drag it back open.
- **`PanelCard`** — the one panel shell every Browse/Viewport/Selected panel renders through. Flat (thin border, minimal radius, no shadow) — not a floating SaaS card.
- **`CommandRibbon` + `DropdownMenu`** — replaced the old full-height `PageHeader` entirely. A single 40px bar: dropdown-triggered menus (Metrics, Filters) on the left, page label + avatar on the right. Only one dropdown open at a time. `PageHeader` still exists, still used by `ComingSoonPage` (on disk, unused by any route now — see §6.9).
- **`SimplePage`** (`framework/ui`) — the shell for pages that don't fit `FeaturePage`'s Browse/Viewport/Selected `Workspace` shape: `CommandRibbon` + a plain scrollable content area. Built once Analytics/Administration/Reports all needed the identical shape at once — see §6.9.
- **`BrowseList`** — **two permanent, independent display modes**:
  - `indent` (flat list, manually-specified depth) — for DAG/sequence data where a single-parent tree would misrepresent it. Genealogy stays on this permanently (the real registry data means Framing-Package has 2 material parents, Sub-Assembly has 4).
  - `children` (real nested tree, expand/collapse per node) — for genuine one-parent containment or real groupings. Construction (Project→Building/Floor), Robotics (each ATC→its real `tools[]`), Logistics (by real `zone`), Assets (by real `category`). Factory's own Browse structure is being reworked as part of the manifest-driven rewrite (§6.3) — its prior "Line→Machines via `lineId`" grouping was fixture-only and doesn't correspond to anything in the real twin, which has no line concept at all.
- **`ToolbarShell` / `ToolbarInput` / `ToolbarSelect` / `ToolbarButton`** — shared flat toolbar primitives, all 8 feature toolbars.
- **`StatusBadge`** — one status pill component, `tone: "positive" | "warning" | "critical" | "neutral"`.
- **`SelectionContext`** — one global selection engine, discriminated union keyed by `feature`, every payload fully typed (no `unknown`, no casting). Manufacturing's payload is fully generic since §6.15 (`{name, extras}`, no per-project fields) — the other 7 features keep their own typed per-kind payloads.
- **`router/routes.tsx`** — single array of `{path, label, icon, element}`, consumed by both `<Routes>` and `Sidebar`'s nav list. Order: Manufacturing, Factory, Robotics, Logistics, Construction, Genealogy, Scheduling, Assets, Analytics, Reports, Administration (reordered, no path/element changes).

### 6.3 Digital Twin — Milestone B, manifest-driven architecture (in progress)

**Why the original first slice got replaced:** the initial Twin Bridge slice (documented in the prior handoff) worked, but hardcoded exactly 7 subsystem identities into `twinTranslator.ts` by name. That meant every time the Python twin grew, someone would have to manually go edit the FF frontend to notice — the opposite of what was wanted. The standing requirement going forward: **the OS must reflect the twin's real complexity dynamically, never via FF-side code hardcoded to today's subsystem list.**

**Twin-side manifest — DONE, verified, real:**

## 7. Standing Engineering Discipline

- **A second, simultaneous react-three-fiber `<Canvas>`/WebGL context in this environment is not reliably stable — confirmed via a repeated, real `THREE.WebGLRenderer: Context Lost.` console error, not assumed.** §6.16's shop-drawing sheet tried a real mini `<Canvas>` per sheet (alongside the always-mounted main `GeometryViewport` Canvas); the math was verified correct at every layer (real logged camera/box values, correctly-sized and positioned DOM canvas element, no CSS clipping/visibility issue) yet the sheet rendered visibly blank — and `toDataURL()`/pixel readback confirmed the canvas buffer was genuinely empty, not a readback-timing artifact. The real cause only surfaced by reading the dev server's own console output, where `Context Lost` was firing repeatedly. **When a second Canvas is genuinely required in this app, don't assume it'll be as stable as the first — verify live, and have a WebGL-free fallback in mind** (§6.16's fix: compute the real 2D projection directly from `geometry.attributes.position` + `matrixWorld` and draw it as SVG — no second renderer needed at all, and arguably more correct for a line-drawing "shop drawing" convention than a shaded 3D render would have been anyway).
- **A blank/broken render with no console errors doesn't mean "no bug" — it means keep escalating the diagnostic, in order: DOM/CSS state, then buffer readback, then the dev server's own terminal output, not just the browser console.** The dev-tools browser console can look completely silent while the real error (`Context Lost`, a stale-HMR `ReferenceError`) is sitting in the Vite terminal output the whole time. §6.16 only found the real cause by reading `tasks/<id>.output` directly after DOM/CSS/pixel-level browser diagnostics had already ruled out everything else.
- **three.js's `GLTFLoader` sanitizes `Object3D.name` on load (spaces become underscores, among other changes) — a real, silent transformation, not a passthrough of the source glTF's own `node.name`.** Confirmed live in §6.14/§6.15: "Walls — literal 2D trace" loaded as "Walls_—_literal_2D_trace". Any mechanism that treats `Object3D.name` as the real, authored, user-facing identity needs to independently verify that assumption (or route the real name through `extras`/`userData` instead, as §6.15 did) rather than trust it silently matches the source file.
- **When two of a task's own explicit rules turn out to genuinely conflict on the real, current data — not a hypothetical — stop and ask, don't silently pick one.** §6.15's "no fixups, respect authored visibility" vs. "reproduce every feature Garden Lofts has today" only turned out to conflict after actually checking the real file's current `hide_render`/`hide_viewport` state directly; the conflict wasn't visible from reading the task brief alone. Surfaced it with the concrete finding and let the user make the call, rather than guessing which rule the task author would have prioritized.
- **A real hierarchy's mechanism can differ entirely between source files of the "same" general kind — object-parenting for one, Collections for another — and a genuinely generic parser has to walk whatever the exporter actually produced, not assume one mechanism.** Confirmed via real introspection of the glTF exporter's own RNA properties (not assumed from option names) that `export_hierarchy_full_collections` and `export_extras` are both non-default and both required for this to work at all; verified live, on both real fixtures, by parsing the exported `.glb`'s own binary JSON chunk directly rather than trusting the export log.
- **`useGLTF` (drei) caches by URL string — a server-side file replacement at a fixed path needs the frontend to change the URL it requests, not just rely on the file changing underneath an unchanged URL.** §6.15's pattern: a `useSyncExternalStore`-backed version counter that appends a cache-busting query string and notifies every subscriber on a successful upload — no full page reload needed, no `useGLTF.clear()` needed either, since a genuinely new URL string already bypasses both drei's cache and the browser's HTTP cache.
- **Promote to `framework/` only on a second or third real consumer**, never speculatively.
- **Don't fabricate data where real data exists or is knowable** — extends to derived fields (never fabricate a "down"/fault state the twin doesn't expose) and to entire objects (the 6 rail/ATC nodes with no live data yet are still real and still shown, just honestly empty).
- **`tsc -b --force` after every change; prefer an actual live check (`npm run dev`) over `tsc` alone** whenever the change has a runtime surface — confirmed possible in this environment since the original Twin Bridge slice.
- **Sequence, don't stack.** Every new idea that's arrived mid-task all session has been explicitly deferred to its own milestone rather than absorbed into whatever was in flight.
- **Investigate before building, report real findings before writing code** — for the twin's own codebase and for any FF work depending on an external real data source. This is what caught the object-model mismatch in the first Twin Bridge slice, and what caught the "13 not 7" gap this pass.
- **When a real data source doesn't map cleanly onto an existing shape, use the real shape — don't force it.** Confirmed repeatedly: Construction's real projects, Factory's real subsystem count (twice now — 7 was already a correction, 13 corrected it further), Genealogy's real DAG structure.
- **Never hardcode an external system's current shape into FF when that system can grow.** The specific, hard-learned version of the above principle from this pass: a translator that hardcodes "these are the N things that exist" is already wrong the moment the source system changes, even if it's correct today. Prefer consuming a self-describing manifest/schema over enumerating identities by hand, whenever the source system can plausibly grow.
- **After any crash or interruption, verify real on-disk state before resuming — never assume completion from the last thing that was asked for.** New this pass, for good reason: an agent crashing mid-task doesn't damage saved files, but it does make "what actually got finished" genuinely unknown until checked.
- **A visibility/inclusion toggle left in a source file by a prior authoring session is data, not noise — read why it's set before overriding it, and don't treat all instances of it as the same thing.** From the Manufacturing ingestion pass (§6.5): 219 objects shared the identical `"hidden for residential plan inspection"` tag, but they weren't all the same kind of hidden — the real architecture (columns, balconies) was only `hide_render`-hidden, while one leftover massing block (`GL_Residential_Core`) was hidden more thoroughly (`hide_viewport` too). That distinction was the real signal for what to keep vs. exclude, and it only surfaced by checking each flag specifically rather than restoring everything with one blanket toggle. The same pass also found that an export operator's boolean kwarg (`use_visible`) didn't mean what its name suggested at a glance — verify a tool's actual flag semantics (e.g. via `get_rna_type().properties`) rather than assuming from the name.
- **Don't carry an unverified claim from a task brief into a permanent doc as if it were confirmed.** The Manufacturing brief asserted a specific number (442 total modules) as a settled fact; it couldn't be located in any accessible source file this pass. It's recorded here as an explicitly unverified prior claim (gap #12), not repeated as fact — the same standard Step 0 already applied to the geometry itself.
- **Two systems that look like they share an identity scheme (matching naming convention, same-looking dotted paths) can still diverge in a way that only shows up by reading the actual consuming code, not the producing side.** `cell_manifest.json`'s ids and the twin's real `resolve_target()` matched for 9 of 13 identities and looked like one scheme — reading only the manifest/exporter side would have missed that the 4 robot ids don't actually resolve. The fix (§6.6/§6.7) was reading the consumer (`resolve_target`) directly rather than trusting that a shared-looking convention was actually shared everywhere it was used.
- **A doc that says a prior pass is "unverified after a crash" can itself go stale** — this pass found `useTwinManifest.ts`/`twinTranslator.ts` fully built and working on disk, contradicting this document's own then-current §4 Factory row. Trust `git status`/reading the files/`tsc -b --force` over a doc's last-known status line whenever they might have diverged, and update the doc immediately once checked rather than letting the discrepancy persist.
- **When testing a cross-feature flow backed by in-memory (non-persisted) state, navigate the way a real user would (in-app links), not via a full address-bar reload** — a hard reload legitimately clears in-memory context and will make a real bug (state not actually flowing between features) look identical to the correct empty-state UI. Caught by testing both navigation styles deliberately, not by accident.
- **A freshly-navigated react-three-fiber `<Canvas>` genuinely can look blank for reasons that have nothing to do with the scene at all** — it starts at a raw default size (`300×150`) and resizes asynchronously once its `ResizeObserver` reports the real container size; a screenshot taken immediately after navigation can catch it mid-resize. From Factory's 3D viewport pass (§6.10): direct `canvas.getBoundingClientRect()` inspection resolved this in one check after camera/`Bounds` theories had already burned real debugging time. Check the canvas's actual measured size before assuming a camera/geometry/material bug on a "blank on load" report.
- **`Bounds`/`useBounds()`'s fit mechanisms (both the declarative `fit` prop and the imperative `refresh().fit()` call) are not reliable in this codebase whenever `OrbitControls` is also mounted** — confirmed twice now, independently, in two different R3F viewports (Manufacturing's plan-view camera swap, and Factory's `Bounds`-based framing in §6.10.) Prefer the manual technique proven in both places instead: a ref-based initial camera position + an explicit non-default `OrbitControls` `target` matching the real scene center, set once. Don't spend time trying to make `Bounds` cooperate with `OrbitControls` — reach for the manual pattern directly.
- **A shared page shell can gain a generic override extension point without changing the component it wraps.** `FeaturePage` gained an optional `workspace?: ReactNode` prop for Factory's bespoke 4-panel Gantt layout (§6.11) the same way it earlier gained `extraMenus` for the Instructions dropdown (§6.7/gap #7) — `framework/workspace/Workspace.tsx` itself needed zero changes either time. The pattern: when a real second/third consumer needs a shape the shared component can't express, extend the *wrapper's* prop surface, not the shared component, if the shared component's own contract shouldn't have to grow to cover a one-off case.
- **A nested `react-resizable-panels` `Panel` containing its own differently-oriented `Group` just works** — no library workaround needed to mix a horizontal split and a vertical split in the same layout (Factory's Browse | (Viewport+Inspector / Gantt) shape, §6.11). Confirmed live, including independent `collapsible`/`collapsedSize={0}` behavior on the new nested divider.
- **A panel's content using a fixed pixel height (e.g. `h-[560px]`) instead of `h-full` inside a `react-resizable-panels` `Panel` will silently desync from the real, resizable container the moment that container's size can change** — the `Panel`'s own DOM sizing keeps working correctly (confirmed by reading the compiled library source, not just assuming); only the fixed-height content inside stops tracking it, showing up as dead background space that grows or shrinks with unrelated drags elsewhere in the layout, and can look like a completely different bug (a boundary "bleeding" into a sibling panel, a drag direction that feels "inverted") depending on where in the layout the mismatch happens to be visible. From Factory's Gantt-panel bugfix pass (§6.12): three components (`FactoryBrowse`, `FactoryInspector`, `FactoryGeometryViewport`) had carried a fixed `h-[560px]` forward from before the panel became resizable, and it reproduced in every state including the default one. **When a `PanelCard` (or similar) lives inside a `react-resizable-panels` `Panel`, its root should size with `h-full`, never a fixed pixel height** — a fixed height is only safe in a genuinely fixed-height container.
- **Before concluding a resizable-panels layout bug is a real structural/DOM-tree problem, measure with `getBoundingClientRect()` before/after the actual interaction rather than reasoning from the JSX alone** — Factory's Issue 1 (§6.12) looked, from the task description, like it could be a JSX-nesting mistake (an inner `Group` accidentally scoped wider than intended). Reading the JSX confirmed correct nesting; reading the *compiled* library source (Context-based `Panel`/`Group` wiring, not DOM-id-based) ruled out an id-collision theory; but the conclusive proof was a live `getBoundingClientRect()` diff on the "affected" sibling panel across a full drag range, which showed zero movement — meaning the reported bug was actually a downstream visual illusion from a separate, real bug (the fixed-height issue above), not a defect in its own right. Don't stop at "the code looks right" or "the library internals look right" when a live measurement can settle it directly.
- **`react-resizable-panels`' drag handles respond to `PointerEvent`s dispatched with `pointermove`/`pointerup` fired on `document` (after `pointerdown` on the handle itself), not to a single coarse synthetic drag gesture** — the `computer` tool's `left_click_drag` action did not register at all with this library in live testing (zero layout change before/after). Simulating a real sequence of `pointerdown` → many `pointermove` steps → `pointerup`, with `buttons:1` set during the move events, worked reliably and is the pattern to reach for when a browser-automation drag needs to move a `react-resizable-panels` separator programmatically.
- **A local Node bridge that only ever served `GET` needs `Access-Control-Allow-Headers` the moment it gains a real `POST` + JSON body endpoint** — `Access-Control-Allow-Origin`/`-Methods` alone (already present in `twin-bridge` for its GET routes) are not sufficient for a real `Content-Type: application/json` POST, which triggers a browser preflight `OPTIONS` request the server must separately answer with `Allow-Headers: Content-Type`. Without it, every real dispatch fails with a generic network error that looks identical to "the bridge isn't running" — cost real debugging time in Track B (§6.17) before the actual cause (a missing response header, not a dead process) was found.
- **`_last_error`-style "last error, overwritten only by the next error" fields are not safe to read as "my dispatch's result" by command name alone** — a real, unrelated, already-stale error can sit there indefinitely, and while the twin is paused its `frame` number is frozen too, so a genuinely fresh rejection and an old stale one can share both the same command name *and* the same frame. Track B's fix (`twinExecute.ts`): capture the full real error object *before* dispatching and compare all its fields, not just the command name, to tell a new failure from a stale leftover.
- **Don't require observing a real multi-tick operation "in progress" before trusting its absence as "done" — it can start and finish between two polls.** Track B's executor originally required seeing a manual-move key present in `manual_moves` before treating its later absence as completion; a real `gantry_move_x` covering a small real distance completed inside a single 200ms poll gap and was never observed present, producing a false "timed out" report for a command that had already genuinely succeeded. The real completion signal is simpler: after a settle delay long enough to guarantee at least one real dispatch cycle has run, absence + no fresh error **is** completion, because the real dispatch code always either registers the move or sets an error — never neither.
- **When a generated multi-command sequence's ordering assumes a capability the real gate logic doesn't actually support, that only surfaces by dispatching it for real.** Track B generated `gantry_hook_grab → gantry_move_x → ...`, which reads as a plausible "pick up and carry" sequence — but the twin's real `gantry_move_x/y` gate requires `state=="PARKED"`, which `hook_grab` immediately leaves. Static generation logic and `tsc` both accepted this without complaint; only a real dispatch against a live twin produced the real rejection that revealed the manual command vocabulary has no real carry-while-moving capability at all. **Generated code that calls real, gated commands needs at least one real dispatch pass before being trusted, the same standard applied to everything else in this document.**
- **A legacy cosmetic field and a new real-identity field can coexist indefinitely without either being wrong, as long as neither is mistaken for the other.** The twin's `tool_idx` (a 5-value color-cycle counter, no real tool identity, confirmed deliberate — Construction_Enterprises' own doc calls it out explicitly) kept working unchanged the entire time real tool identity (`ATCSubsystem`'s named `Tool` children, `mounted_tool`) was being built out around it in a separate pass. Phase F's real dispatch command correctly used `tool_name`, not the original vocabulary proposal's `tool_idx` — the fix wasn't reconciling the two fields, it was recognizing early which one was ever real. When two fields in the same object model look like they might describe the same thing, check which one actually carries real identity before wiring a new consumer to either.
- **`Box3().setFromObject()` on a freshly-mounted react-three-fiber object, called from `useLayoutEffect`, can race the render loop and return a box in local (untransformed) space instead of world space** — confirmed live via Construction's map (§6.21): R3F hasn't necessarily run a render pass yet at the moment a layout effect fires on mount, so a descendant's cached `matrixWorld` can still be stale/identity. If that wrong box gets cached in component state and the effect's dependency array doesn't cover "time has passed since mount" (only real prop changes, e.g. position), the wrong value persists for the object's entire lifetime — it never self-corrects just because later frames render correctly. Fix: call `object.updateWorldMatrix(true, true)` (parents and children) immediately before `setFromObject`, forcing fresh transforms rather than trusting whatever's cached. This is a different failure mode from the already-known "Box3 is world-space but rendered inside an already-translated parent, so subtract the translation or it applies twice" bug (documented inline in the same `SiteGroup` component) — that one is a math/space bug, this one is a timing/staleness bug — but both are worth checking together anywhere else in this codebase computes a `Box3` from a freshly-mounted or freshly-moved object (Manufacturing's and Factory's `SelectionOutline` use the same `Box3.setFromObject` pattern and have since been checked against this specific race — both confirmed accurate, the issue is isolated to the map's fresh-mount case only).
- **Auto-normalizing a color ramp against a dataset's own local min/max always produces maximum visual contrast, regardless of whether the real underlying variation is dramatic or genuinely tiny — this overstates flat data, the same category of dishonesty as fabricating a number.** Confirmed in Construction's map (§6.22): North Texas's real elevation range (74–393m, ~319m variance) stretched to full 0–1 color contrast read like a heat map, implying dramatic relief that isn't there. Fix: normalize against a real, fixed, meaningful reference scale instead (here, sea level to the real high point of the contiguous 48 states) — so a genuinely small local range only occupies a small slice of the ramp, correctly reading as flat, and the same ramp stays valid for future real data with more actual variation without redesigning it.
- **An equirectangular projection with a longitude scale fixed at one reference latitude is fine at a small regional extent and measurably wrong at continental scale — check the real math before assuming "it was fine before" still holds at a bigger extent.** Confirmed in Construction's map (§6.22): `cos(32.8°)` fixed for all latitudes was ~1.3% off across North Texas's own ~2.25° span (negligible, correctly disclosed as such originally) but ~28% off at the continental US's ~49°N edge once the USA backdrop was added. Fix: compute the longitude scale from each point's own latitude. This didn't require an iterative/approximate inverse either — since the projection's z-axis encodes only latitude, the real latitude can be recovered first and exactly, which then gives the exact scale needed to recover longitude too. Widening a map's real extent is exactly the moment to re-derive whether an existing "negligible at this scale" simplification still holds — don't just reuse it because it worked before.
- **three.js `Text` (troika-three-text) `fontSize` is a world-space size, not a screen-relative one — a label sized to read well at one camera distance can be genuinely unreadable at another, and "make it visible" and "make it usable at the zoom level where someone would actually want to read it" are different bars.** Confirmed in Construction's map (§6.22): US state name labels sized proportionally to the existing ~100km county labels (`fontSize=9`) were essentially invisible at the zoomed-out whole-country view — exactly the zoom level where reading a state's name is the point. Size real map/scene labels for the real-world scale of what they're labeling and the zoom level they're meant to be read at, not just scaled down from a smaller, already-working label elsewhere in the same scene.
- **A hypsometric/heatmap-style color ramp needs BOTH a real fixed reference scale AND real perceptible hue/saturation on its stops — fixing only one half still fails.** Confirmed live in Construction's map (§6.22/§6.23): normalizing against a real fixed reference (Mount Whitney) alone still read as flat grey, because the specific stops that reference range actually lands on (`#dadfd2`, `#ddd8c8`) turned out to be ~17–24% saturation — technically colored, perceptually neutral. Computed real HSL values to confirm this rather than eyeballing a screenshot. The fix needed both halves together: real perceptible hues on the stops that actually matter for the real data range, AND (separately) enough real local-data resolution (going from a 16×16 to a 48×48 elevation grid) for the result to show real texture instead of a smooth wash. Neither alone was sufficient — verified by testing after each fix independently, not assuming the first fix covered it.
- **Prisma 7 removed `datasource.url` from `schema.prisma` — a real, undocumented-until-checked breaking change from earlier Prisma major versions.** Confirmed live: `prisma validate` failed with error code P1012 the moment a schema written against the old convention was tried. Connection config now lives in a separate `prisma.config.ts` (`defineConfig` from `prisma/config`), and the client needs an explicit driver adapter (`@prisma/adapter-pg` for Postgres) rather than Prisma's old built-in Rust engine. Fetched Prisma's real current docs directly rather than guess the new shape from memory of older Prisma versions — infra config is exactly the kind of thing where a wrong guess costs more time than a documentation check up front.
- **A real initial Prisma migration can be generated and structurally verified without ever touching a live database.** `prisma validate` and `prisma generate` (Prisma Client codegen) both need only the schema file, not a connection. `prisma migrate diff --from-empty --to-schema <path> --script` produces the real SQL a first `migrate dev` would apply, purely from the schema — used when no local Postgres was reachable (enterprise migration Phase 2, §8) to get a real, reviewable migration file into the repo rather than blocking all progress on environment availability. Real distinction preserved in every report about this: "structurally validated" is not the same claim as "confirmed by actually applying it" — said explicitly, not blurred, until the live apply actually happened.
- **`npm install`'s `allow-scripts` policy can silently block a package's postinstall step (engine binaries, platform-specific native builds) without failing the overall install** — confirmed live: Prisma's CLI reported real engine binaries as present in `node_modules` but `npx prisma --version` didn't fully resolve until `npm approve-scripts` was run for `prisma`/`@prisma/engines`/`esbuild` explicitly. If a freshly-installed CLI tool behaves as if a build step never ran, check for this before assuming a real install failure.
- **A Windows feature enablement (WSL2, in this case) reporting "successful" is not the same as the feature being active — both `wsl --install`'s own real output ("Changes will not be effective until the system is rebooted") and Docker's own engine (which depends on WSL2) said so explicitly.** Stopped and reported rather than attempting `docker compose up` against an engine that couldn't possibly be running yet, and did not restart the machine unprompted — that's the user's call, not an automatic step to take just because a tool said a restart was needed.
- **A design doc's proposed command can already be superseded by state the system exposes some other way — check before building the literal proposal.** The original command-vocabulary brief specified a standalone `rail_move` command (Phase C, §6.20); investigating first found real rail position was already exposed via each robot's own `rail_x` field (from the kinematics merge, §6.18), making a dedicated move-the-rail-alone command redundant with something that already existed. Building the literally-specified command would have added a second, parallel way to reach the same real state — investigate what the system already exposes before implementing a proposal at face value, even one written by a careful, domain-informed author.
- **A Node/tsx script that constructs its own DB client (e.g. `new PrismaPg({ connectionString: process.env.DATABASE_URL })`) needs its own `import "dotenv/config"` — env vars loaded by a wrapping config file (`prisma.config.ts`) don't reach a script run standalone.** Confirmed live in Phase 2 (§8): `prisma db seed` worked (goes through `prisma.config.ts`, which does load dotenv, first) but `tsx prisma/seed.ts` run directly failed with a real, specific error (`SASL: ... client password must be a string`) because `DATABASE_URL` was undefined in that process. The npm script alias for the same direct invocation had the identical latent bug. Fix was one line (`import "dotenv/config"` at the top of the script itself) — the lesson is to check this whenever a script's env-dependent behavior differs by *how* it's invoked, not just fix the one invocation path that was tested.
- **Two independent "broadcast a plain window event, let other modules react" mechanisms can form a real infinite feedback loop the moment one of them reacts to the other unconditionally — confirmed live, not a theoretical risk (§16): the backend's own request log grew by ~43,500 lines in a few seconds.** `AuthContext`'s new `SESSION_EXPIRED_EVENT` handler broadcast the pre-existing `AUTH_CHANGED_EVENT` on every fire; `constructionSiteStore.ts`'s pre-existing `AUTH_CHANGED_EVENT` listener unconditionally refetches on every fire, with no concept of "did the status actually change." A failed request → session-expired → auth-changed → refetch → still failed → session-expired → ... closed a real loop, each lap taking only as long as a local network round-trip. **Any handler that reacts to "state changed" by re-broadcasting or re-fetching must check whether the state genuinely changed before acting — reacting unconditionally is what turns two independently-reasonable one-way event mechanisms into a cycle.** The fix here tracked the previous value in a ref (the listening effect only registers once, so a plain closure over state would see a permanently-stale value) and skipped the broadcast/refetch entirely on a no-op transition. A defense-in-depth cooldown was added on top (`authFetch.ts`, §16) specifically so a *future* cascade of this same shape, from code that hasn't been written yet, can't repeat this at the network layer even if the same class of bug slips in again somewhere else.

### 10. Enterprise migration Phase 3b — real email/password auth + JWT sessions, real RBAC enforcement, live-verified

**Schema**: `User.passwordHash` (argon2, never seeded in `seed.ts` — that file is checked into git and must never carry even a hashed real credential) and a new `RefreshToken` table (`tokenHash` — a SHA-256 digest, never the raw token, same "never store the raw credential" principle as passwords; `revokedAt` nullable, never deleted on revoke, so reuse-after-revoke is a real, detectable event). Migration `20260725040848_phase3b_auth`, applied and confirmed live via `psql`.

**`jose` over `jsonwebtoken`** for the access-token JWT: native ESM (matches this repo's `"type": "module"`), built on the standard Web Crypto API rather than a Node-only Buffer implementation, and a modern promise-based API — `jsonwebtoken` is CommonJS-first and callback-oriented. Refresh tokens are deliberately **not** JWTs — a real random 32-byte token, opaque to the client, looked up by its hash in `RefreshToken`; this is what makes real server-side revocation possible at all (a self-contained JWT can't be un-issued before it expires on its own).

**`backend/scripts/create-user.ts`** — the only real way to create an account (masked password prompt via `@inquirer/prompts`, email + role-select from the 10 real seeded roles, argon2-hashed before writing). **Auth endpoints** (`backend/src/routes/auth.ts`): `POST /auth/login` (argon2 verify against a real **precomputed dummy hash** when the email doesn't exist at all, so an unknown-email attempt takes the same real `argon2.verify()` time as a wrong-password one — a real, well-known timing side channel, not a hypothetical one, closed alongside the login failure message's own deliberately generic wording), `POST /auth/refresh` (real rotation — the presented token is always revoked, whether or not a new one issues, so it's a genuine one-time credential), `POST /auth/logout` (real server-side revoke + cookie clear, idempotent), `GET /auth/me` (real user + role + resolved `role_permission` grants, grouped by module).

### 16. Real automatic session refresh — a real gap found live, plus a real infinite-loop bug caught before it shipped (committed `291a31b`, live-verified)

**Real bug reported live, not hypothetical:** signed in as CEO, but selecting a project in the new left "Construction Projects" panel showed "Not authenticated" for every category. Reproduced directly rather than guessed: the access-token JWT (15-min TTL, `backend/src/lib/jwt.ts`) had genuinely expired, and **nothing in the frontend ever refreshed it automatically** — confirmed by reloading and watching `GET /auth/me` itself come back a real `401`. **`src/lib/authFetch.ts` (NEW)** — wraps every real authenticated call to the ff-backend (confirmed via grep: `AuthContext`'s `fetchMe`, `constructionSiteStore.ts`, `projectFilesApi.ts` — the three real consumers) with a retry-after-refresh policy: a real `401` triggers exactly one real `POST /auth/refresh` (the existing §10 rotation endpoint); on success the original request is transparently retried once; on failure, broadcasts `SESSION_EXPIRED_EVENT` so `AuthContext` can flip to a real signed-out state. Concurrent 401s (e.g. Construction's 4 parallel document fetches all expiring at once) share one in-flight refresh call — real refresh-token rotation means a second concurrent attempt would present an already-superseded cookie and fail.

**A real infinite-loop bug found and fixed live, before this shipped — not a hypothetical risk, a confirmed one:** the first version of `AuthContext`'s `SESSION_EXPIRED_EVENT` handler broadcast `AUTH_CHANGED_EVENT` unconditionally. Live-tested by triggering a real logout while watching the backend's own request log — it grew by **~43,500 lines in a few seconds**. Root cause, confirmed by reading the actual log sequence: a failed request fires `SESSION_EXPIRED_EVENT` → `AuthContext` broadcasts `AUTH_CHANGED_EVENT` unconditionally → `constructionSiteStore.ts`'s own pre-existing `AUTH_CHANGED_EVENT` listener unconditionally refetches (it has no concept of "did the status actually change") → that refetch, still genuinely unauthenticated, 401s again → `authFetch` tries another refresh, fails again → `SESSION_EXPIRED_EVENT` fires again → repeat, as fast as the local network round-trip allows. **Fixed at the real source, not papered over:** `AuthContext` now tracks `status` via a ref (its event-listener effect only registers once, so a plain closure would've seen a permanently-stale value) and only broadcasts on a genuine authenticated→unauthenticated transition, never a redundant "still logged out" reconfirmation. Also added a real defense-in-depth cooldown directly in `authFetch.ts` (3 seconds after any failed refresh, every subsequent `401` is treated as "still dead" with zero network round-trip) so no future cascade of this shape — from this code or anything else — can hammer the server again, regardless of what triggers it.

**Live-verified, both the fix and the original gap it closes:** temporarily dropped `ACCESS_TOKEN_TTL` to `8s` (`tsx watch` auto-restarted the backend on save) to get a fast, fully real test instead of waiting out the real 15 minutes — signed in fresh, waited past the real expiry, reloaded, and confirmed the page rendered correctly with **zero visible error**, the real 401→refresh→retry cycle happening invisibly (confirmed in the backend's own request log: one `401`, one `POST /auth/refresh`, one successful retry). Reverted `ACCESS_TOKEN_TTL` back to `15m` afterward, confirmed via `git diff --stat` that the revert left zero trace before committing. `tsc -b --force` clean throughout, no console errors.
